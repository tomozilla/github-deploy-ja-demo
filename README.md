# github-deploy-ja-demo

[English](README.md) | [日本語](README.ja.md)

**Personal learning record, unofficial (個人の学習記録・非公式).** I am a fellow builder who tried this myself. This is not official guidance and not an authority.

A tiny repo for trying the Supabase dashboard's **GitHub integration** ("Route A"): connect a repo to a project from the dashboard, merge a SQL file, and see it applied. No CLI is typed by the reader and no token or database password is copied anywhere. It also contains a small static page, the **deploy board**, that compares the repo's migration files with what the database says it applied.

Last run and checked: **2026-10-31**.

## Files

| Path | What it is |
|---|---|
| `supabase/migrations/*.sql` | Four fake sample migrations (a `notes` table, an `author` column, a fix, an index) |
| `supabase/config.toml` | Generated by `supabase init`, plus `[functions.applied-migrations] verify_jwt = false` and an experiment (`max_rows = 7`, see below) |
| `supabase/functions/applied-migrations/index.ts` | Read-only Edge Function that lists the applied migrations (deployed by the integration, because it is declared in `config.toml`) |
| `app/index.html`, `app/board.js` | The deploy board (plain HTML/JS, no build) |
| `app/config.example.js` | Copy to `app/config.js` (git-ignored) and fill in |
| `ja/` | Copies of the code with Japanese comments / UI strings |

## Prerequisites
- A Supabase project (the Free plan is enough for Route A).
- A GitHub account and a repo with a `supabase/` folder (`config.toml` + `migrations/`).
- For the preview-branch part only: a Pro-plan organization.

## Steps (Route A, dashboard only)
1. Project Settings -> Integrations -> GitHub -> choose the repo. The first time, "Add GitHub Repositories" opens GitHub's install page for the Supabase app: choose **Only select repositories** and pick just this repo.
2. Leave Working directory as `.`, keep "Deploy to production" on and the production branch as `main`, press **Enable integration**.
3. Open a pull request that adds a file to `supabase/migrations/` and merge it. The integration applies every migration that is not yet applied, in file-name order (including older files that were already in the repo).
4. Check Database -> Migrations in the dashboard, and the "Supabase Preview" check on the merge commit in GitHub.

## What I observed (2026-10-31, Free project, then a Pro test)
- Merging applied all pending migrations in order. The merge commit got a "Supabase Preview" check that ended `success`.
- A broken migration (duplicate column) was **not caught on the PR** on the Free plan (the check was "skipped"). It was caught **after the merge**, on `main`, as a failed check with the real Postgres error. The dashboard showed no error.
- While the broken file stays in the repo, **every later migration fails too** (the same old error), because migrations run in order. Fixing the file in place (it had never been applied) and merging again applied everything.
- An Edge Function declared in `config.toml` was deployed by the integration, with `verify_jwt = false` honored.
- A dashboard-only setting changed in `config.toml` (`[api] max_rows`) was **ignored**: the dashboard still showed 1000.
- On a Pro project the same screen enables branching by default. A PR with a broken migration produced a preview branch, and the failure appeared **on the PR before merging** (a bot comment with a task table, and a failed check).

## Cost
- Route A on the Free plan: **$0** (measured: nothing was billed in my run; GitHub integration works on all plans per the docs).
- Preview branches (Pro plan): the docs say there is no fixed fee for a branch, only the usage it incurs; a branch on Micro compute starts at **$0.01344 per hour**, and branch compute is **not covered by the spend cap** (docs, checked 2026-10-31). A new Micro project in a Pro org is the same rate (about $10 per month).
- My run: one extra Micro project for about 15 minutes and one preview branch for about 2 minutes, both deleted right after. Calculated at the docs rate this is a few cents at most. I did not read the final invoice, and I did not verify whether partial hours are rounded up.
- The deploy board's own cost: none on Supabase's side except one Edge Function call per refresh. It makes 2 GitHub API calls per refresh; GitHub allows 60 unauthenticated requests per hour per IP, so there is **no auto-refresh**.

## Security notes (demo shortcuts)
- The Edge Function has **Verify JWT off** and only checks for the project's *publishable* key. A publishable key is public by design, so this is only an entry ticket, **not authentication**. Safer: keep Verify JWT on and call it with a signed-in user's token, or do not expose it at all.
- The Supabase GitHub app asks for read access to code and metadata and read/write on actions, checks, pull requests and workflows. Install it for **selected repositories only**.
- `app/config.js` holds the project URL and the publishable key. It is git-ignored; never put a secret (service_role) key there.
- The sample table has RLS on and only an authenticated read policy. It is fake data only.

## Cleanup
Disable the integration (Settings -> Integrations), delete any throwaway project and preview branch, delete the Edge Function, drop the sample table, and uninstall the Supabase app from your GitHub account if you do not need it (github.com/settings/installations).
