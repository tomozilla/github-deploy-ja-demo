# github-deploy-ja-demo

**個人の学習記録・非公式です。** 同じ立場のつくり手として自分で試した記録で、公式の案内でも、権威ある解説でもありません。

SupabaseダッシュボードのGitHub連携（「ルートA」）を試すための小さなリポジトリです。ダッシュボードからリポジトリをつなぎ、SQLファイルをマージして、反映されるところまでを見ます。つなぐ作業にCLIは要らず、トークンやデータベースのパスワードをどこかに貼ることもありません（`config.toml` を作るために、手元で `supabase init` を1回だけ使いました。手書きは試していません）。リポジトリ内のマイグレーションファイルと、データベースが「適用済み」と答える内容を見比べる静的ページ「デプロイボード」も入っています。

最終実施・確認日: **2026-10-31**

## ファイル

| パス | 内容 |
|---|---|
| `supabase/migrations/*.sql` | 架空のサンプル4本（notesテーブル、author列、修正、インデックス） |
| `supabase/config.toml` | `supabase init` で生成。`[functions.applied-migrations] verify_jwt = false` と実験用の `max_rows = 7` を追加 |
| `supabase/functions/applied-migrations/index.ts` | 適用済みマイグレーションを返す読み取り専用のEdge Function（`config.toml` に書いてあるので連携が自動でデプロイ） |
| `app/index.html`, `app/board.js` | デプロイボード（素のHTML/JS、ビルドなし） |
| `app/config.example.js` | `app/config.js`（git管理外）にコピーして使う |
| `ja/` | 日本語コメント・日本語UIのコピー |

## 前提
- Supabaseプロジェクト（ルートAはFreeプランで足ります）
- GitHubアカウントと、`supabase/`（`config.toml` と `migrations/`）を持つリポジトリ
- プレビューブランチを試す場合のみ、Proプランの組織

## 手順（ルートA、ダッシュボードだけ）
1. Project Settings → Integrations → GitHub でリポジトリを選びます。初回は「Add GitHub Repositories」でGitHubのインストール画面が開くので、**Only select repositories** を選んでこのリポジトリだけを指定します。
2. Working directory は `.`、「Deploy to production」はオン、本番ブランチは `main` のまま **Enable integration** を押します。
3. `supabase/migrations/` にファイルを足すプルリクエストを作ってマージします。連携は「まだ適用されていないマイグレーション」を、ファイル名の順にすべて適用します（連携を有効にする前からリポジトリにあった古いファイルも含みます）。
4. ダッシュボードの Database → Migrations と、GitHubのマージコミットの「Supabase Preview」チェックを確認します。

## 見えたこと（2026-10-31、Freeプロジェクト＋Proでの検証）
- マージすると、未適用のマイグレーションが順番にすべて適用されました。マージコミットの「Supabase Preview」チェックは `success` でした。
- 壊れたマイグレーション（列の重複）は、Freeプランでは**プルリクの段階では検出されず**（チェックは「skipped」）、**マージ後に** `main` 上で、本物のPostgresエラー付きの失敗チェックとして出ました。ダッシュボード側にはエラーは出ませんでした。
- 壊れたファイルがリポジトリに残っている間は、**後ろの正しいマイグレーションも全部失敗します**（同じ古いエラー）。順番に実行されるためです。まだ一度も適用されていないファイルをその場で直してマージしたら、すべて適用されました。
- `config.toml` に書いたEdge Functionは連携が自動でデプロイし、`verify_jwt = false` も反映されました。
- `config.toml` で変えたダッシュボード専用の設定（`[api] max_rows`）は**無視**されました。ダッシュボードは1000のままでした。
- Proプロジェクトでは同じ画面でブランチ機能が最初からオンです。壊れたマイグレーションのプルリクでプレビューブランチが作られ、失敗は**マージ前のプルリク上**（ボットのコメントとタスク表、失敗したチェック）に出ました。

## 費用
- FreeプランでのルートA: **0ドル**（実測: 私の実行では課金なし。公式ドキュメントでもGitHub連携は全プランで使えます）
- プレビューブランチ（Proプラン）: ドキュメントでは、ブランチ自体の固定費はなく、使った分だけの課金です。Microコンピュートのブランチは**1時間あたり0.01344ドル**から、ブランチのコンピュートは**スペンドキャップの対象外**です（ドキュメント、2026-10-31確認）。ProのOrganizationに追加するMicroプロジェクトも同じ単価（月約10ドル）です。
- 私の実行: 追加のMicroプロジェクトを約15分、プレビューブランチを約2分動かし、どちらもすぐ削除しました。ドキュメントの単価で計算すると、多くても数セントです。請求書の確認はしておらず、1時間未満が切り上げかどうかも確認していません。
- デプロイボード自体: Supabase側の費用は更新1回につきEdge Function 1回だけです。GitHub APIは更新1回で2リクエスト、認証なしだとIPあたり1時間60回までなので、**自動更新はしません**。

## セキュリティ上の注意（デモ用の近道）
- Edge Functionは **Verify JWTをオフ** にし、プロジェクトの*公開用（publishable）*キーの有無だけを確認しています。公開用キーは公開される前提のものなので、これは入場券にすぎず、**認証ではありません**。安全にするには、Verify JWTをオンのままログイン済みユーザーのトークンで呼ぶか、そもそも公開しないでください。
- SupabaseのGitHubアプリは、コードとメタデータの読み取り、Actions・チェック・プルリクエスト・ワークフローの読み書きを求めます。**選んだリポジトリだけ**にインストールしてください。
- `app/config.js` にはプロジェクトURLと公開用キーが入ります。git管理外にし、秘密鍵（service_role）は絶対に入れないでください。
- サンプルのテーブルはRLSオンで、ログイン済みユーザーの読み取りポリシーだけです。データはすべて架空です。

## 片付け
連携を無効にし（Settings → Integrations）、使い捨てのプロジェクトとプレビューブランチ、Edge Function、サンプルのテーブルを削除します。不要ならGitHubからSupabaseアプリもアンインストールします（github.com/settings/installations）。
